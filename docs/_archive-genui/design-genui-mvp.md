## Problem Statement

표면상의 문제 정의는 "AI 에이전트가 만든 시간 기반 의도가 알림·텍스트·스크립트로
흩어져, 사용자가 지속적으로 실행·수정·확인·공유할 surface가 없다"이다 (PRD 3장).

세션에서 드러난 **진짜 동력**은 다르다. 사용자 본인의 시간 기반 의도는 이미 GWS
CLI로 대부분 처리되고 있다. 실제 추진력은 *"GenUI를 손에 잡히게 구현하고
사람들에게 경험시키고 싶다"*는 욕구다. 즉 이 프로젝트는 pain-first 스타트업이
아니라, governed GenUI 런타임을 마스터하고 시연하려는 **builder-first 프로젝트**이며,
스타트업 가능성은 옵션으로 열어둔다.

이 재정의가 MVP 범위를 바꿨다 (아래 "What Makes This Cool" + "Recommended Approach").

## What Makes This Cool

핵심 whoa: **같은 파이프라인이 의도마다 시각적으로 완전히 다른 surface를 만든다.**
"15분 뒤 세탁기 확인"은 카운트다운 화면이 되고, "Polymarket 재미있는 주제 정리"는
완전히 다른 브리핑 화면이 된다 — 그리고 그 화면을 **AI가 catalog 안에서 조립**한다.

선택된 접근(C: Spec-diff Theater)은 이 마법을 숨기지 않고 노출한다:
`의도 텍스트 → 실시간 생성되는 GenUI spec JSON → 조립되는 surface`를 3분할로 보여줘,
"AI가 저 화면을 만들었네"가 추론이 아니라 눈앞에서 증명되게 한다.

whoa의 진짜 청중은 알람을 보는 일반 사용자가 아니라, intent→spec→render 투명성에
감탄하는 **기술 청중(공동창업자·AI비즈 수업·개발자)**이다.

## Constraints

- 7일 데모 창 (PRD 17장 주간 계획 기준, 단 범위 수정 반영).
- 사용자는 다중 프로젝트 병행 중 (Fevio, Campsite, Go-Push, Unveil 등) — 시간 예산 빠듯.
- MVP는 라이브가 아니라 **녹화 가능한 데모**가 성공 기준.
- mock/fixture 데이터 허용 (실제 외부 API 불필요).

## Premises (전부 합의됨)

1. 목표는 즉각적 스타트업 검증보다 GenUI를 손에 잡히게 만드는 구현/시연이다.
2. PRD의 `alarm.basic only` MVP는 "알람 앱"처럼 보여 GenUI를 드러내지 못한다.
   1순위 whoa(다른 의도→다른 화면)를 증명하려면 시각적으로 대조되는 Pack이 최소 2개
   필요하다.
3. 증명할 기술 핵심은 닫힌 루프다:
   `intent → catalog-governed GenUI spec → render → feedback → runtime state`.
   notification/scheduler/marketplace가 아니다.
4. push 알림, 정확한 cron scheduler, 마켓플레이스, Flutter/Native는 MVP 보류.
5. 성공 = "AI가 저 화면을 만들었네" 반응이 나오는 녹화 가능한 데모. 수요 지표가 아니다.

## Approaches Considered

### Approach A: Demo-thin (결정론적 템플릿)
LLM 없이 `intent → 미리 정의된 spec 템플릿`에 파라미터 채움. 7일 안에 확실히 끝나고
데모가 안 깨지지만 **GenUI가 아니다** — 조건부 템플릿 렌더링이며 배우고 싶던 어려운
부분(governed LLM 생성)을 전혀 다루지 못한다. Effort S / Risk Low.

### Approach B: Real GenUI (catalog-governed LLM 생성)
실제 LLM이 pack의 `allowed_widgets` catalog로 제약되어 spec 생성 + Zod 검증, catalog
밖 위젯 참조 시 거부·재생성. whoa가 진짜이고 스타트업 옵션이 열리는 유일한 경로.
Effort M / Risk Med (LLM 지연·변덕으로 라이브 데모 깨질 위험).

### Approach C: B + Spec-diff Theater — **선택됨**
B를 핵심으로 하되 의도→spec JSON→surface 3분할 시각화로 메커니즘을 노출, 녹화 데모의
설득력을 극대화. B 의존. Effort B + S / Risk Med.

## Recommended Approach

**Approach C (B + Spec-diff Theater).**

근거: 사용자의 명시적 목표 "GenUI를 손에 잡히게 만들고 경험시키고 싶다"에 A는 부합하지
못한다(템플릿엔 GenUI가 없음). B가 진짜 학습·시연 가치를 담고, C는 그 가치를 녹화
데모에서 가장 강하게 드러낸다.

### 수정된 MVP 범위 (사용자 co-authored)

두 개의 대조되는 Pack:
- **`alarm.basic`** — 시간 기반 intent, 단순·빠른 action feedback.
- **`daily-brief.basic`** — 알람과 시각적으로 완전히 다름, GenUI 느낌 강함. 실제
  Polymarket API 불필요, fixture/mock 데이터로 충분.

| Pack | 명령 | 위젯(catalog) | feedback |
|---|---|---|---|
| alarm.basic | `mycron create --pack alarm.basic --after 15m "세탁기 확인"` | Countdown, BigTime, Snooze, Complete, History | snooze, complete |
| daily-brief.basic | `mycron create --pack daily-brief.basic --topic "..." --schedule "daily 08:30" --lang ko` | BriefHeader, TopicCard, EvidenceDrawer, MoreLikeThis, LessLikeThis, MuteTopic, History | save_topic, mute_topic, more_like_this, less_like_this |

### 아키텍처 (그릴 개정 — 생성은 host agent, MyCron은 서빙)

원래 Approach C는 MyCron 백엔드가 LLM을 호출해 spec을 생성하는 그림이었으나, 그릴에서
생성 주체가 **host agent**로 이동했다 (ADR-0001). 개정된 흐름:

```
[host agent (Hermes 등) — LLM 소유]
  → mycron schema <pack>        : Widget Catalog 조회 (런타임 introspection, ADR-0003)
  → agent가 catalog 참조해 GenUI Spec(선언적 JSON) 생성        (생성·LLM = agent 부담)
  → mycron create --json '{cronlet + spec}'    : agent-first CLI, raw-JSON (ADR-0003)
[MyCron 서버 — 서빙 런타임]
  → ingestion 검증: Spec을 Widget Catalog로 검증, catalog 밖·악성 입력 거부 (ADR-0002)
  → cronlet + spec 영속화 (Account 스코프 스토어)
  → 웹: cronlet 목록 표시 → 사용자가 선택 → 이미 생성된 surface 렌더
  → PWA 렌더러: spec JSON → MyCron 소유 catalog 컴포넌트 매핑 (allowed 밖 렌더 거부)
  → 사용자 action → POST feedback → feedback_events 저장 → runtime state/history 갱신
  → [Theater 레이어] 의도 텍스트 / 전송된 spec JSON / 렌더된 surface 3분할 노출
       — fakery가 아니라 "진짜 도는 governed 계약"의 정직한 시각화 (CONTEXT.md 참조)
```

CLI는 cronlet 스토어에 대한 CRUD 클라이언트(`login/list/get/create/update/delete` +
`schema`) — Drive에서 파일 쓰고 지우듯 (ADR-0003).

스택 (PRD 12장 기준): Next.js PWA + TS, Supabase Postgres, Zod(ingestion 검증).
**MyCron은 LLM을 호출하지 않는다** (비용·소스 = agent). 스케줄러는 MVP에서 단순화
(클라이언트 카운트다운 + daily-brief는 fixture 즉시 표시).

## Open Questions

- ~~**LLM 생성의 catalog 제약 방식**~~ — RESOLVED (ADR-0002/0003): agent가 `mycron schema`로
  조회한 Widget Catalog에 맞춰 선언적 spec을 생성하고, MyCron은 ingestion에서 검증·거부.
  제약은 catalog 발행 + ingestion 검증의 양면으로 닫힘.
1. **Theater 연출 — 실시간 vs replay** — 실제 agent 생성 과정을 보여줄지, 전송된 spec을
   replay해 안정적으로 보여줄지. (안전망: replay 권장.)
2. **ingestion 거부 시 fallback** — invalid spec 거부 시 어떤 안전 surface를 보여줄지(빈
   화면 금지). P3 시연의 일부.
3. **두 pack의 "대조" 강도** — daily-brief에 카드·드로어 등 알람에 없는 위젯이 실제로
   필요. catalog 설계 시 의도적 대비 확보.
4. **(장기 thesis) Demand Gate 정의** — "commitment"의 주체·측정(요청자 stake vs 집계
   수요), 대기 중 누가 Pack을 만드는지. post-MVP, 별도 그릴 필요.

## Success Criteria (그릴 개정 — "쇼케이스"에서 "실제 확장 기술 증명"으로)

목표가 whoa 데모에서 *포장 아닌 진짜 확장 가능한 기술 증명*으로 이동했다. 데모가
증명해야 할 핵심은 **P1(Pack 확장성) + P3(Governed 안전성)**.

**P1 — Pack 확장성 (확장이 진짜임을 증명):**
1. host agent가 `mycron schema <pack>`로 Widget Catalog를 조회하고 그에 맞는 GenUI
   Spec(선언적 JSON)을 생성한다
2. 서로 다른 두 Pack(alarm.basic, daily-brief.basic)이 시각적으로 완전히 다른 surface로
   렌더된다
3. **코어(렌더러/서버) 수정 0으로 3번째 Pack을 추가** — schema + catalog 엔트리만으로
   새 surface가 같은 계약을 타고 흐른다
4. 각 surface에서 action 클릭 → feedback_events 저장 → runtime state/history가 실제로 바뀜

**P3 — Governed 안전성 (포장 아닌 진짜임을 증명):**
5. catalog 밖 위젯/깨진·악성 Spec을 ingestion에서 **거부하는 걸 실제로 시연** (하드닝 작동)
6. MyCron은 LLM을 호출하지 않음을 증명(생성·비용은 agent 측)

**시각화(권장, fakery 아님):**
7. Theater 3분할에서 의도 → 전송된 spec JSON → 렌더된 surface가 투명하게 보임 —
   실제 도는 governed 계약의 정직한 시각화

## Long-term Thesis (그릴 피봇 — 수요 게이트 마켓플레이스)

P1(누구나 계약으로 Pack 추가)은 slop 범람 위험(PRD 리스크 #16)을 낳는다. 피봇된 장기
방향: Pack은 자유 자가공개가 아니라 **수요로 게이트된다.** 사용자가 surface를 *요청*하고
(Pack Request) → *대기* → commitment/수요가 임계(Demand Gate)를 넘으면 → 마켓플레이스에
published. 이 한 메커니즘이 두 문제를 동시에 푼다 — **품질(slop 차단)** 과 **수요 검증**.

이것은 office-hours 세션이 짚은 MyCron의 유일한 약점(수요 증거 0)을 제품 메커니즘 안에
내장한다: 제품이 곧 수요 발견 기계가 된다. **MVP 비범위** — 단, 데이터 모델에 Pack
`status`(draft→requested→pending→published) + demand 카운터 자리를 지금 남겨 둔다
(ADR-0001, forward-compat). Demand Gate의 구체 정의는 별도 그릴 대상(Open Question #4).

## Distribution Plan

MVP 산출물은 **녹화 데모 영상 + 로컬/Vercel 배포된 PWA**다. 바이너리 배포 없음.
- PWA: Vercel 배포 (Next.js, 기존 파이프라인으로 충분).
- CLI: 로컬 Node 패키지로 충분 (공개 npm 배포는 MVP 비범위 — agent write-port 데모용).
- 공유·설치(Pack marketplace)는 명시적 보류 (whoa #4, 로드맵 Phase 4).

## Next Steps (수정 7일 계획)

- **Day 1:** Widget Catalog + 두 Pack 정의(`allowed_widgets`/`actions`/`feedback_events`,
  status+demand 자리 포함) + DB schema (cronlets, ui_specs, feedback_events).
- **Day 2:** agent-first CLI — `login/list/get/create/update/delete` + `mycron schema <pack>`
  (Widget Catalog 런타임 introspection), raw-JSON 입력.
- **Day 3:** ingestion 검증 (Zod, catalog 밖·악성 spec 거부 = **P3 핵심**) + cronlet/spec
  영속화. (생성은 agent 쪽 — MyCron은 LLM 호출 안 함.)
- **Day 4:** PWA 렌더러 (spec→MyCron 소유 catalog 컴포넌트, allowed 밖 거부) — 두 화면.
- **Day 5:** feedback API + runtime state/history 갱신.
- **Day 6:** Spec-diff Theater 3분할(replay) + **P1 시연**: 코어 수정 0으로 3번째 Pack 추가.
- **Day 7:** P1(3-pack 확장) + P3(악성 spec 거부) 시나리오 녹화.

## The Assignment

(빌더 버전 — 실세계 1행동)

**오늘, 코드 한 줄 쓰기 전에:** `alarm.basic`과 `daily-brief.basic` 두 Pack의
`allowed_widgets` catalog를 손으로 적고, 각각의 GenUI spec JSON을 **목(mock)으로 직접
한 개씩 써본다.** 그리고 그 두 JSON을 나란히 놓고 본인에게 물어라 — *"이 둘이 보는
사람에게 시각적으로 충분히 다른가? 이게 같은 알람 앱처럼 보이지 않는가?"* 만약 두
spec이 비슷해 보이면, 데모는 실패한다. 이 30분이 7일 전체의 성패를 가른다. 코드보다
대비(contrast) 설계가 먼저다.

## What I noticed about how you think

- 당신은 "내가 매일 겪는 문제다"라고 답했지만, 곧바로 *"비슷한 경험을 별도의 앱으로
  만들고 gen ui를 경험시키고 싶다"*고 했다. 이 정직함이 세션의 방향을 살렸다 — 대부분은
  자기 동력이 기술 욕구임을 끝까지 인정하지 않고 가짜 수요 서사를 붙든다. 당신은 한 번
  찔렀더니 바로 진짜를 내놨다.
- 전제 2(alarm-only는 GenUI를 못 드러낸다)를 던졌을 때, 당신은 동의에 그치지 않고
  `AlarmKit + DailyBriefKit Lite` 조합과 수정 성공 기준 8개를 *직접 다 써냈다.* 이건
  agency다 — 진단을 받고 실행안으로 즉시 변환하는.
- PRD의 깊이(Pack Schema, renderer-agnostic contract, governed catalog)는 이 공간을
  안에서 아는 사람의 것이다. 위험은 단 하나, 그 깊이가 *수요가 아니라 아키텍처에 대한
  애착*에서 나온다는 점 — 그래서 builder-first로 정직하게 프레이밍한 게 옳았다.
